# NOMAD V0.6.5-B/C/D — implementation and acceptance report

This implementation keeps the existing eDEX HUD, repository model, terminal transport, security profiles and application registry. There are no dependency changes or commits. Pre-existing V0.6.5-A login work was preserved.

1. **AutomationEngine architecture.** `src/classes/automationEngine.js` coordinates inspection, single-use setup plans, authorization, supervised execution, verification and the project projection. Plans are held in main memory and expire after two minutes. At most 128 pending plans and 64 operation records are retained. It accepts trusted repository IDs and internally sealed plans, never renderer command strings. Control Plane remains the action/confirmation authority.

2. **Project adapter architecture.** `src/classes/projectAdapters.js` supplies `ProjectAdapter`, `NodeProjectAdapter`, `PythonProjectAdapter` and `RustProjectAdapter`. The interface contains `detect`, `inspect`, `buildSetupPlan`, `buildRunProfiles`, `fingerprintInputs` and `verifyReady`. Detection reads bounded regular files with non-following, non-blocking descriptors, checks file identity, and never imports Python, invokes package scripts, builds Cargo or evaluates config. Mixed projects retain existing RUN choices but automatic setup refuses ambiguous project-type selection.

3. **Node automation.** Detects `package.json`, `packageManager`, npm/pnpm/yarn locks and only `dev`, `start`, `serve`, `preview`. Conflicting manager evidence is refused. npm uses `ci` with a lock and `install` otherwise. pnpm/Yarn Classic use frozen locks when present; modern Yarn uses immutable installation and skip-builds mode. Default PREPARE requests lifecycle suppression. The separate **PREPARE + HOOKS** action creates a new explicit plan allowing lifecycle scripts for projects that need them. Plans identify declared lifecycle hook names; package-manager config/plugins and dependency build code remain execution risks. No runtime or package-manager bootstrap is installed automatically.

4. **Python automation.** Detects pyproject, requirements, requirements-dev, Pipfile, Poetry lock, `main.py` and `app.py`. Plans create/repair a project `.venv`, install declared requirements or the pyproject package, and run `pip check`. This never modifies system Python or uses sudo. The existing trusted Python executable launches a fixed main-owned bootstrap into the sandbox's `.venv`; paths are not caller supplied. Venv RUN requires STRONG isolation. Pipfile/Poetry-only setups are explicitly unsupported rather than guessed.

5. **Rust automation.** Fixed `CARGO RUN` and authorized `cargo build`; builds use `--locked` when Cargo.lock exists. Cargo.toml, Cargo.lock, build.rs and Cargo configuration participate in fingerprints. Cargo scripts/proc macros are acknowledged as executable code. Cargo release, Go and CMake adapters were not added.

6. **Clone auto-inspection.** The existing trusted GitHub clone still performs its validations. Successful clone decoration now includes project metadata automatically; the existing clone/Git-state refresh path updates repositories. Control Plane shows the detected project and PREPARE/RUN/CODE/INFO controls. Clone does not invoke setup or RUN. Pull decoration also re-inspects.

7. **Project registration/projection.** PROJECTS is a derived view keyed by opaque repository ID, not a replacement repository database. It exposes type, runtime/manager, fixed profile labels, isolation and readiness. Selection updates the assistant's existing selected-repository context. Successful setup records a session-local readiness stamp; changed inputs produce `PROJECT CHANGED / REINSPECTION REQUIRED`. Repositories are re-derived after restart; there is no new persistent project registry.

8. **Setup authorization and fingerprints.** Setup is always separately authorized, including default installs with lifecycle suppression. Tokens bind repository execution identity, full input fingerprint, current security profile and exact main-owned typed steps. Confirmation consumes the token; replay, expiry, changed inputs or a changed profile refuse execution. Inputs are checked again before every dependent executable step. RUN keeps the existing fingerprint/trust store and separate authorization. Node fingerprints now include the full manifest and locks; Python includes manifests, requirements and fixed entrypoint content. Run authorization dialogs no longer expose executable/argument fields.

9. **Setup isolation and credentials.** Setup requires verified Bubblewrap STRONG isolation even in NORMAL. There is no direct or systemd fallback for setup. Only the current repository is writable at `/workspace`; HOME/TMP/cache are sandbox-local, host home/other repositories/SSH-agent and credential environment are absent. System runtime mounts retain the existing Bubblewrap policy. Network is shared only for dependency installation/build steps; venv creation and runtime verification retain an isolated network namespace. Network-enabled steps can contact the host network; this is not an egress firewall. Environment is allowlisted. Credential-like failures report `CREDENTIALS REQUIRED / AUTOMATIC SECRET EXPOSURE REFUSED`; no credential broker exists.

10. **Application auto-registration.** `ApplicationAutomationService` coordinates the existing catalog installer, desktop discovery, reconciliation, learner and hot reload. Successful package-manager completion is followed by identity verification. Automatic registration requires a root-owned, non-writable desktop entry and trusted executable ancestry; the verified executable is pinned in the registry. User-controlled entries require the ADD TO NOMAD confirmation path. Package installation success and registration success are separate outcomes; missing/conflicting identity reports registration incomplete.

11. **WM_CLASS automation.** Verified StartupWMClass is used directly. Otherwise the existing learner launches the validated application, correlates windows/process ancestry and stores exact class/instance only for an unambiguous result. The learner checks security policy before launch and before writing. Ambiguous learning leaves the application unavailable and reports incomplete registration. No renderer matcher or PID is accepted.

12. **External discovery.** Non-recursive watchers monitor configured XDG application directories and the registry parent. Fixed-path metadata polling handles directories/registry files created after startup. Entries are verified for file ownership, modes, symlinks and size. New candidates appear in APPS with ADD TO NOMAD / IGNORE, and live events mark the APPS trigger. Discovery alone never launches unknown applications. Ignore is session-local.

13. **Live registry reload.** Install, add, learn and filesystem changes reload the existing validated registry, update i3's application set and emit the existing launcher-change event. Existing RegistryStore atomic writes, 0600 permissions, ownership checks, symlink rejection and malformed-config preservation are retained. No session restart is needed for normal registry changes.

14. **Assistant and provider boundary.** Spanish/English preparation, dependency setup, RUN, STOP, inspection, CODE, pull-then-run, installation, registration, discovery and scan phrases map to named TrustedActionRegistry actions. Unknown/shell/sudo/curl-pipe requests execute nothing. Future provider proposals still permit only `actionId` and `targetId`; shell, command, executable, args, path, env, sudo, PID and signal fields are rejected. Main adds exactly three automation IPC requests: status, cancel and log, each taking one opaque operation ID. Progress is an event. Existing sender ownership checks remain in force.

15. **Multi-step plans/transactions.** Python visibly sequences environment, dependency installation, runtime verification and project registration; Node/Rust use their fixed installation/build steps plus verification/registration. Steps progress through PENDING/RUNNING/SUCCESS/FAILED/SKIPPED. Failure prevents dependent steps. `haz pull y ejecútalo` means confirmed pull, success check, re-inspection and the existing RUN trust decision; a changed fingerprint requests fresh authorization. There is no shell chain. Dependency rollback is explicitly unavailable; the implementation neither deletes an existing `.venv` nor automatically uninstalls system packages. Registry removal remains an explicit existing action.

16. **Cancellation, logs and responsiveness.** Setup uses the existing RepositoryProcessManager and its bounded TERM/KILL process-group supervision. CANCEL accepts only the operation ID; RUN/PULL cannot overlap an active setup. Cancellation is checked across awaited repository resolution and between steps. Profile changes stop the active setup. UI updates immediately and receives stage transitions; it does not wait for setup completion before returning control. Operation output retains the last 65,536 characters in memory; the current setup step writes at most 64 KiB to `setup.log` under the existing repository state root, mode 0600. VIEW LOG renders execution output as text. System-package installation reports factual install/discovery/learning stages, not invented download percentages, and is not advertised as cancellable/rollbackable.

17. **Security profiles.** NORMAL allows explicitly authorized setup with STRONG isolation. PUBLIC also requires the boot session's verified ephemeral path routing; switching from a NORMAL session may require restart before setup. Repository writes are explicit in the plan. LOCKDOWN blocks setup/RUN, external install, registration and launch; read-only inspection/discovery and stopping an already tracked process remain available. Confirmation also refuses a changed security profile. No V0.6 policy minimum was lowered.

Integration changes: `src/_boot.js`, `src/preload.js`, `src/_renderer_secure.js`, `src/classes/controlPlaneService.js`, `controlPlaneView.class.js`, `intentParser.js`, `trustedActionRegistry.js`, `repositoryService.js`, `repositoryRunProfileService.js`, `repositoryProcessManager.js`, `repositoryIsolationService.js`, `desktopEntryDiscovery.js`, `rendererDiagnostics.js`, `src/cli/installService.js`, `windowClassLearningService.js`. New tests: `test/projectAutomation.test.js`, `applicationAutomation.test.js`, `automation.gui.js`. Updated tests: intent parser, repository run actions/profiles, application registry/discovery/CLI/post-install/WM_CLASS fixtures, and the existing secure GUI harness. This report is new. The working tree also contains the user's pre-existing login files/changes; they are not newly attributed to B/C/D.

Existing tests exercise the process supervisor, isolation, Git defenses, trust stores, renderer, telemetry, terminal, login, Control Plane and profile policies. `node --check` passes on all 144 JavaScript files found outside dependency/build directories. `git diff --check` passes. 20. **Real GUI acceptance.** The production Electron renderer was exercised inside a private authenticated Xwayland/i3 session. The earlier complete run passed login/reveal, isolation, terminal round trip, keyboard/native shortcuts, Control Plane, repository selection, real generic application/VLC management and 30 seconds of advancing CPU/RAM/network/globe/graph measurements. The expanded automation run uses an authored temporary Node repository: automatic project projection, no pre-authorization marker, explicit setup, real Bubblewrap npm ci, suppressed lifecycle, progress, separate RUN authorization, real RUN/STOP, explicitly authorized long lifecycle cancellation, external desktop discovery, live registration and LOCKDOWN refusal. This is a real local fixture, **not** a claimed live GitHub clone or system-package installation. Actual package-install authentication, remote GitHub clone/pull, dedicated GDM login, and real Python/Rust dependency builds still need the manual VM checks below. 21. **Exact manual VM checklist.** Use a disposable VM snapshot with NOMAD's existing trusted runtimes/Bubblewrap and a configured catalog source. Perform the following in order; never use a real/private credential-bearing repository for acceptance.

    1. Enter the dedicated NOMAD GDM/i3 session in NORMAL. Confirm login waits for ENTER and the original terminal, keyboard, side panels and globe remain visible after reveal.
    2. Use + REPOSITORY to clone a small disposable **public GitHub repository you own/reviewed**, containing one top-level Node project and a harmless marker lifecycle script. Authorize CLONE only. Confirm the repo and PROJECTS entry appear without refresh; the marker must not exist.
    3. Select it in PROJECTS. Use Ctrl+Space → `qué necesita este repo`. Check manager, lockfile/profile, setup state and actual isolation.
    4. Say `prepara este repo`. Inspect the fingerprint, lifecycle policy, network/write effects and fixed steps. CANCEL the plan; verify no dependencies or marker were created.
    5. Repeat and AUTHORIZE. Check immediate stage acknowledgement, continued clock/telemetry, VIEW LOG and successful completion. The lifecycle marker must still be absent for default PREPARE.
    6. For the reviewed marker fixture only, select PREPARE + HOOKS and review/authorize its distinct warning. Check the marker appears only after this authorization. For a reviewed long-running hook, use CANCEL and verify all tracked setup children stop while an unrelated application remains alive.
    7. Ctrl+Space → `corre este repo`. Confirm separate RUN authorization; authorize and observe its known output. Say `para este repo`; verify it stops.
    8. Change the relevant manifest/lockfile in the disposable upstream. Say `haz pull y ejecútalo`, authorize PULL, and verify changed execution inputs trigger a second RUN authorization. CANCEL it and verify no process starts. Repeat with a dirty repository; pull failure must prevent RUN.
    9. Repeat PREPARE/RUN/STOP with reviewed minimal Python (`main.py`, requirements) and Rust (Cargo.toml/Cargo.lock) repositories. Verify Python writes only project `.venv`; inspect Cargo's build-script warning. Test missing runtime/modules: expect an explicit failure, never runtime auto-install or system Python modification.
    10. In the disposable VM only, say `instala spotify` (or choose an available catalog app). Review source/package and authorize. Complete the host's existing package-manager authentication if available. Check factual stages, verified desktop identity, WM_CLASS/learning and live launcher registration. If authentication/source/identity is unavailable, confirm truthful failure or `INSTALLATION SUCCESS / NOMAD REGISTRATION INCOMPLETE`, not READY.
    11. Install another harmless desktop app through the VM's normal package manager. Check the APPS notification; say `qué programas nuevos hay`, ADD TO NOMAD and confirm. Verify launcher appearance without restarting. For a fixture without StartupWMClass, check exact learner results; two genuinely ambiguous windows must leave registration incomplete.
    12. Remove the fixture registry entry using NOMAD and verify immediate disappearance. Say `actualiza la lista de programas`; confirm read-only discovery offers it again. IGNORE should suppress the prompt for this session.
    13. Create a setup plan, switch profile, then attempt its confirmation. It must require reauthorization. Boot a correctly routed PUBLIC session and repeat setup; if ephemeral routing/Bubblewrap is unavailable, verify setup is blocked rather than downgraded.
    14. Select LOCKDOWN. Repeat prepare/run/install/add/open and verify refusal. Stopping previously tracked processes must remain possible. Try `ejecuta sudo ...`, `haz curl ... | bash`, `corre este comando`, `ejecuta rm -rf ...`, `instala este .sh`; verify no trusted action runs.
    15. Return to NORMAL through the existing profile flow. Recheck terminal, Ctrl+Space, virtual keyboard, CODE/INFO/GITHUB, launcher, CPU/memory/network/globe updates. Record which real package sources, Python/Cargo runtimes and GDM session were actually tested. Restore the disposable snapshot after acceptance; NOMAD must not claim it rolled back dependency or system-package changes.

22. **Remaining automation limits.** No runtime/bootstrap installation, credential broker, Poetry/Pipenv/Go/CMake adapter, automatic multi-project setup selection, durable transaction recovery or automatic dependency rollback. Readiness stamps/history/ignore decisions are session-local. READY denotes completed supported setup (or detected existing Node dependency directory), not proof every application function works. Full source trees and transitive local configuration references are not hashed; authorized repository code remains untrusted and sandboxed. Catalog installation still uses the existing host package-manager authentication mechanism; a GDM session without suitable authentication cannot silently install and will fail. Rootless/ambiguous desktop identities require explicit registration instead of automatic trust. Real remote clone/pull, system installs and real Python/Rust builds were not substituted with fabricated GUI successes.
